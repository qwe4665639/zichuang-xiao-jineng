# Agent 插件 GitHub 周榜 / 月榜

产出物：一份**给非程序员看**的中文榜单，前 10 名。每条要让人看完就知道两件事 —— **这事跟我有没有关系**，**我该说句什么话把它用起来**。

## 先记住读者是谁

**读者不是程序员。** 他不装软件、不敲命令、不看 README 里的配置段、不关心协议和钩子。他手上只有一个 AI 助手，习惯是"把东西丢给 AI，说一句人话"。

所以：

- **不写安装方式**。报告里不出现任何命令，也不出现"通过 MCP 接入""装个 hook""改配置文件"这类描述。
- 读者唯一需要的"技术信息"是**一条能丢给 AI 的网址**。
- 判断一条写得合不合格，就问一句：**一个不写代码的人读完，知不知道该在什么时候、说句什么话把它用起来？**

## 硬规则（违反即返工）

1. **零编造**。星标、网址、场景、触发说法都要能对回本次会话的工具返回。
2. **每条必须有三样**：可直接安装的**入口网址** + **≥2 个具体使用场景** + **怎么开口启用它**。
3. **不写安装方式**。只给网址，最多加一句"把这条链接丢给你的 AI，说帮我装上"。
4. **禁止照搬 README 的示例**。README 的示例是写给开发者的（假定读者会敲命令、懂术语）。场景要自己从它的能力**翻译**成"谁在什么处境下会想要它"。
5. **星标是快照**，标注抓取时间与口径；周榜月榜各自独立。
6. 抓不到的源写进"未能覆盖"，不许静默省略。

## 第 0 步：先问口径（不可跳过）

用 `ask_user_question` 一次问清：

- **统计范围**：`本周（本周一 → 今天）` / `本月（当月 1 日 → 今天）` / `两个都要`
- 仅在用户表述含糊时才追问：只算"可直接安装的插件"，还是也纳入"生态基建"（技能评测、安全扫描、插件分发 CLI）

同时用 `pwsh` 取本地日期算窗口，写进报告：

- 本周起点 = 本周一 00:00，周号 `YYYY-Www`（ISO 周，与 `插件话题周榜_2026-W38.md` 这类既有文件名一致）
- 本月起点 = 当月 1 日
- 记下快照时刻 `T_snap`；之后所有"X 星"都标注 `T_snap`

## 第 1 步：建候选池（多源交叉，别只用一招）

完整查询矩阵与可粘贴代码见 `references/query-cookbook.md`。源与用途（均为本环境实测结论）：

| 源 | 能拿到什么 | 取用方式 |
| --- | --- | --- |
| `mcp__github__search_repositories` | 结构化仓库元数据、星标、topics、时间 | **首选** |
| `mcp__github__search_code` | README 正文片段（**返回正文，可用**） | 判断"它能干什么、要什么前置条件"的首选 |
| `mcp__github__list_commits` / `list_releases` | 窗口内是否有提交/发版（证明"本期还活着"） | 逐条核实，`since=<窗口起点>` |
| `https://github.com/trending?since=weekly\|monthly` | **真实窗口涨星**（页面里的 "N stars this week/month"）+ 窗口热度榜 | shell 抓取后本地解析；页面约 700 KB，**不要**用 `web_fetch` 灌进上下文 |
| `https://api.github.com/...`（search / readme / contents） | 搜索替代、README 正文、目录清单 | shell 直取，见手册；未认证搜索限速实测 **10 次/分钟** |
| `web_search` | 第三方榜单转述、线索 | 只作线索，结论必须回到 GitHub 验证 |
| ~~`web_fetch`~~ | **本环境对 GitHub 不可用** | `github.com`、`raw.githubusercontent.com` 均报 `resolves to a non-public IP address`，改用 shell HTTP |
| ~~`mcp__github__get_file_contents`~~ | 返回 embedded resource，模型读不到正文 | 读正文改用 readme API / `search_code` |

三路并取候选：

1. **trending 榜** —— 窗口内真实涨星排名，覆盖"老仓库突然爆"。
2. **新星搜索** —— `created:>=<窗口起点>` + 关键词/话题，`sort=stars`，覆盖"新仓库上榜"。
3. **活跃老库搜索** —— `pushed:>=<窗口起点>` + `stars:>=500` + 关键词，补 trending 每期只有 ~25 条的遗漏。

## 第 2 步：筛掉不该上榜的

**纳入**：MCP 服务 / MCP 集成、Agent Skill 包、Claude Code 与 Cursor 等插件、插件市场、其他 harness 插件（DSH、Codex、OpenClaw 等）。
**生态基建**（技能评测、安全扫描、插件分发 CLI）默认不纳入；只有用户明确要时才收，并单独打标签。

**排除**：模型权重与训练代码、与智能体无关的普通库、纯 SaaS 无仓库、fork 与镜像、已 `archived` 的仓库、单纯 awesome-list（清单不是插件）、**不能直接装到自己 agent 上的应用/框架**。

**类型判定**（决定第 3 步"怎么启用"怎么写 —— 先看一眼仓库根目录）：根目录有 `.claude-plugin/` 或 `plugin.json` → 插件形态；有 `skills/` → 技能形态；有 `.mcp.json` / `mcpServers` → 服务形态；有 `.cursor-plugin/` → IDE 插件形态。取根目录清单的命令见手册第 5 节。

## 第 3 步：逐条取证（每条都要过这一关）

对每个候选：

1. 取元数据：`full_name`、`stargazers_count`、`created_at`、`pushed_at`、`topics`、`description`、`license`、`archived`。
2. 读 README，**只提取这四样**：① 它到底能干什么；② 是给谁用的；③ **要用它得先准备什么**（要不要登录、要不要联网、要不要先有素材/数据、要不要打开某个软件）；④ 有没有明确的能力边界。
   **不要提取命令和配置** —— 报告里不写这些。
3. **判定"怎么启用"，按类型套用**（这是全篇最需要动脑的地方）：

   | 类型 | "怎么启用"写成 |
   | --- | --- |
   | 一句话触发的技能（画图、改文风、写汇报） | 触发词是什么：说出哪几个字它就接手；没反应时怎么点名 |
   | 装完自动生效的（输出风格、记忆、上下文管理） | "以后不用管它，它自己作用在你每次提问上" |
   | 要打开某个软件才有的（IDE 插件、桌面应用） | 在哪个场景下会遇到它，你要打开什么 |
   | 市场 / 货架 | "它本身不是工具，是货架 —— 你从里面挑" |
   | 要先喂素材的（记忆、知识库） | 先要给什么，给完之后怎么用 |

4. 证明"本期有热度"：窗口内是否有 release 或 commit（`mcp__github__list_commits`，`since=<窗口起点>`）。返回空数组就是"窗口内无提交"，照实写。
5. 链接可用性：用 shell 发一次 HEAD 请求看状态码（`web_fetch` 在本环境对 GitHub 域一律失败），见手册第 6 节。

## 第 4 步：每条写"场景 + 怎么开口"（最容易做砸的一步）

**每个场景必须回答四件事：谁、在什么处境下、想干什么、以前有多麻烦。** 场景要来自它的真实能力，但翻译成生活和工作的语言。

**怎么启用**写成两句话之内的人话："你只要说……" 或 "装好之后不用管，它自己……"。

**禁止**（照搬 README 的典型症状）：

- 不写 `npx …`、`/plugin …`、`docker …` 这类命令，也不要"安装方式"这一栏。
- 不写"进阶用法：结合 CI 做门禁""通过 MCP 协议接入""配好 hook 后自动捕获"。
- 不写"示例 1 / 示例 2 / 入门 / 进阶"这种开发者文档的分层标题。
- 不把 README 里原本的示例换个说法搬过来。

**正例**（完整样例见 `references/output-template.md`）：

> **你什么时候会用到它**：你要给同事讲清一件事是怎么运转的，资料是散的，以前要么自己画一下午，要么画出来不好意思发。现在你跟 AI 说"把从下单到发货的流程画成一张图，要能放进汇报里的"，图就有了。
>
> **怎么启用它**：不用学新东西，平时怎么跟 AI 说话就怎么说，只要话里带上"画图""画流程""画架构图"，它自己接手。它没反应时，在句子里点个名："用 archify 帮我画一下"。

**凑不出 2 个场景时**：不要硬编。第二个位置改成"**它帮不上忙的地方**"，并说明这是限制说明而不是场景。

## 第 5 步：排序、成稿、交付

- 排序口径写进报告：**窗口涨星**（trending 可见项优先）> **快照星标** > **窗口内提交/发版活跃度**。涨星不可得的条目必须写明"以快照星标为准"。
- 周榜与月榜**各自独立取前 10**，不共用名次。
- 文件名沿用用户既有习惯，写在**工作区根目录**：`插件话题周榜_YYYY-Www.md`、`插件话题月榜_YYYY-MM.md`（两个都要时写两个文件）。
- 结构照 `references/output-template.md`。
- 用 `present` 交付文件，并在回复里给出"**最值得先装的 3 条 + 建议顺序**"，同样用大白话说清"它能帮你干什么"。

## 常见坑

- **最容易犯的错：把 README 的示例搬进报告。** 那些例子假定读者会敲命令、懂术语，对非程序员读者等于没写。
- **读者看不懂的词一律不写**：MCP、hook、CLI、manifest、CI、token、沙箱、渲染、渐进式披露。要说就换成"它是个货架""它自己会记住""图会直接给你一张能发的图片"。
- **trending 页面很大**：`web_fetch` 会把 ~700 KB 灌进上下文。用 shell 抓取并解析，只 print 结果行。
- **本环境的两个硬坑（实测）**：`web_fetch` 对 `github.com`、`raw.githubusercontent.com` 一律报 `resolves to a non-public IP address`；`mcp__github__get_file_contents` 只返回 embedded resource，模型看不到正文。**读正文只能走 `api.github.com` 的 readme/contents 接口，或 `mcp__github__search_code`。**
- **`raw.githubusercontent.com` 不稳**：实测连续 3 次超时、另有 502，不要当主路径。
- **未认证搜索 API 限速 10/min**：一次用 `per_page=30` 拿够，别循环 30 次；整轮梳理的搜索调用控制在 ~6 次以内。
- **trending 没有话题过滤**：话题维度靠 search，窗口涨星靠 trending，必须交叉。
- **星标随时变**：所有数字都带 `T_snap`。
- **"热门"≠"好用"**：每条至少给一句"它帮不上忙的地方"（大白话的风险/成本提示）。
- **星级通胀是常态**：新仓库几天冲到几万星不代表稳定；`license`、`archived`、issue 活跃度要一起看。
